18.Kubernetes DNS
    Pod IPs can change when Pods are recreated.
    Service provides stable access to Pods.
    DNS gives a name to the Service so applications don't need to use the Service IP.
    Service metadata.name becomes its DNS name.

    Example:

    Service name: backend
    DNS name: backend
    Same namespace → backend
    Different namespace → backend.namespace

    Flow:

    App → DNS name → Service → Pods

    Memory: DNS name → Service → Pods

21.Safe kubectl Workflows — Short Notes
    kubectl explain → Get information about a Kubernetes field.
    --dry-run=client → Test locally; request doesn't reach API Server.
    --dry-run=server → Request reaches API Server for validation, but isn't saved.
    kubectl diff → Compare live cluster state vs manifest to see what will change.
    kubectl apply → Actually make the change.
    kubectl get / rollout status → Verify the result.
    Memory cue

    Explain → Preview → Validate → Compare → Apply → Verify

26.Taints and tolations

    Taint = a rule on the Node saying “Pods, stay away unless you are allowed.”
    Toleration = permission on the Pod saying “I am allowed to be here.”

    The 3 taint effects:
        NoSchedule = don't allow
        PreferNoSchedule = preferably don't allow
        NoExecute = don't allow + evict

30.NetworkPolicy

    Q1. What happens if no NetworkPolicy exists?
    All pods can communicate freely.

    Q2. Can NetworkPolicy block traffic to Services?
    NetworkPolicies are enforced on pods, not Services. Traffic reaching a Service is ultimately evaluated against the backend pods' policies.

    Q3. Does NetworkPolicy work without a supporting CNI plugin?
    No. The cluster's CNI plugin must implement NetworkPolicy enforcement.

    Q4. Can multiple NetworkPolicies apply to the same pod?
    Yes. The allowed traffic is the union of all rules from all NetworkPolicies that select the pod.

    Q5. Is NetworkPolicy stateful?
    Yes. If ingress is allowed, the corresponding response traffic is automatically allowed, and similarly for allowed egress connections.

    values.yaml → Configuration

34.Pod Disruption Budget (PDB) 

    PDB protects application availability during voluntary disruptions by ensuring a minimum number of Pods remain available.

    minAvailable → Minimum number of Pods that should remain available.
    maxUnavailable → Maximum number of Pods that can be unavailable at the same time.
    Voluntary disruption → Planned Pod eviction, such as node maintenance or kubectl drain.
    Important: PDB does not protect against unexpected Pod crashes or node failures.

35.Kustomize vs Helm 

    Kustomize:
        Customizes existing Kubernetes YAML files.
        No templates required.
        Uses base + overlays for different environments.
        Think: "Customize my existing YAML."

    Helm:
        Packages Kubernetes resources into Charts.
        Uses templates + values.yaml.
        Good for reusable application deployments.
        Think: "Package and deploy my application."

    Kustomize → Customize YAML
    Helm      → Package + Template + Deploy

36.Mounted Files

    Mounted files allow Kubernetes to make ConfigMap/Secret data available as files inside the Pod.

    ConfigMap/Secret → Volume → File inside Pod
    Kubernetes can update the mounted file when the configuration changes.
    The application must reload/read the file again to use the new value.
    If the application doesn't support reload → restart the Pod.

    Memory:
        Mounted file = Config/Secret available as a file inside the Pod

37.Security Context
    Security Context defines how a Pod/Container runs and what privileges it has.

    runAsUser → Run container as a specific Linux user.
    runAsNonRoot: true → Prevent container from running as root.
    readOnlyRootFilesystem: true → Container cannot modify its root filesystem.
    allowPrivilegeEscalation: false → Prevent processes from gaining higher privileges.
    capabilities → Add or remove specific Linux privileges.
    Can be configured at Pod level or Container level.
    Main Goal:
        Follow the principle of least privilege — give the container only the permissions it actually needs.

38.Pod Security Admission Levels

    Security level increases from left → right:

    Privileged → Baseline → Restricted

    Privileged 🟢 → No/very few restrictions; allows highly privileged Pods.
    → Used when maximum flexibility is needed.
    Baseline 🟡 → Blocks common dangerous settings.
    → Good basic security for normal applications.
    Restricted 🔴 → Strongest security; requires Pods to follow strict security best practices.
    → Best for security-sensitive workloads.
    Easy to remember

    Privileged = Allow almost everything
    Baseline = Block dangerous things
    Restricted = Allow only secure configurations

39.Lifecycle Hooks

    Lifecycle Hooks = actions executed during container start/termination.

    Hook	When?	Purpose
    postStart	After container starts	Initialization/setup
    preStop	Before container stops	Cleanup/graceful shutdown

    Easy memory:

    postStart → STARTUP action

    preStop → SHUTDOWN action
