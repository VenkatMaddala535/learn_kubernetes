12.Application Probes — Short Notes
    Readiness Probe → Checks whether the application is ready to accept traffic.
        Failure → Pod is removed from Service endpoints.
        Container is not restarted.
    Liveness Probe → Checks whether the application is still working/alive.
        Repeated failure → Container is restarted.
    Startup Probe → Checks whether the application has finished starting.
        Useful for slow-starting applications.
        While startup probe is running, liveness/readiness probes are not acted on.
    Common settings
        periodSeconds → How often the probe runs.
        initialDelaySeconds → Wait before the first probe.
        failureThreshold → Number of consecutive failures before failure is declared.
        successThreshold → Number of consecutive successes required.
        timeoutSeconds → Maximum time allowed for one probe.

    Startup = Started? | Readiness = Ready for traffic? | Liveness = Still alive?

    # 1. Startup Probe
          startupProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 10

    # 2. Readiness Probe
            readinessProbe:
                httpGet:
                    path: /
                    port: 80
                periodSeconds: 5

    # 3. Liveness Probe
            livenessProbe:
                httpGet:
                    path: /
                    port: 80
                periodSeconds: 10

13.Environment Variables & Configuration Volumes
    Environment Variable = configuration value provided to the container process.
        Can come directly from YAML, ConfigMap, or Secret.
        Available when the container starts.
        Changing the ConfigMap/Secret does not change an existing environment variable.
        Usually requires a Pod restart/rollout.
    Configuration Volume
        Configuration Volume = ConfigMap/Secret mounted as files inside the container.
        Useful for configuration files, certificates, etc.
        Mounted files can eventually update when the ConfigMap/Secret changes.
        Application must reread/reload the file to use the new value.
        subPath mounted files do not automatically update.

    ENV → value → restart needed
    Volume → file → can refresh → app must reread

29.Vertical & Node Autoscaling

    HPA = Copies | VPA = Size | Node Autoscaler = Machines

    HPA
    Changes the number of Pods.
    Example: 2 Pods → 5 Pods.
    Usually reacts to CPU, memory, or other metrics.
    VPA
    Changes/recommends CPU and memory resources for a Pod.
    Example: 500m CPU → 1 CPU.
    It does not create more Pods.
    VPA Off = recommendation only; it doesn't change the Pod.
    Node Autoscaler
    Changes the number of nodes/machines.
    First, Kubernetes tries to place Pods on existing nodes.
    If no suitable node has enough capacity → Pod becomes Pending.
    Autoscaler can then add a suitable node.

30.NetworkPolicy — Short Notes
    NetworkPolicy controls Pod-to-Pod communication.
    Without a policy, Pods can generally communicate with each other.
    Ingress = traffic coming into a Pod.
    Egress = traffic going out of a Pod.
    Source Pod = Egress, Destination Pod = Ingress.
    Labels + podSelector identify which Pods the policy applies to and which Pods are allowed.
    namespaceSelector is used when controlling traffic between different namespaces.
    Common approach: Default Deny → explicitly allow required traffic.

    NetworkPolicy
    │
    ├── Ingress → traffic INTO the Pod
    ├── Egress  → traffic OUT of the Pod
    │
    ├── podSelector
    │   └── identifies Pods using labels
    │
    └── namespaceSelector
        └── identifies a namespace

    Allows only backend → database:

        apiVersion: networking.k8s.io/v1
        kind: NetworkPolicy
        metadata:
        name: database-policy
        spec:
            podSelector:
                matchLabels:
                    app: database

            policyTypes:
                - Ingress

            ingress:
                - from:
                    - podSelector:
                        matchLabels:
                            app: backend

34.Pod Disruption Budget (PDB) 

    PDB protects application availability during voluntary disruptions by ensuring a minimum number of Pods remain available.

    minAvailable → Minimum number of Pods that should remain available.
    maxUnavailable → Maximum number of Pods that can be unavailable at the same time.
    Voluntary disruption → Planned Pod eviction, such as node maintenance or kubectl drain.
    Important: PDB does not protect against unexpected Pod crashes or node failures.

    PDB protects application availability during planned/voluntary disruptions.
    minAvailable → minimum Pods that must remain available.
    maxUnavailable → maximum Pods that can be unavailable.
    Example: replicas: 5, minAvailable: 4 → during maintenance, Kubernetes tries to keep at least 4 Pods available.
    Voluntary disruptions → kubectl drain, node maintenance, planned eviction.
    ❌ Does not protect against unexpected Pod crashes or node failures.

    Easy memory:

    Replicas = how many Pods I want.
    PDB = how many Pods I can safely lose during maintenance.

36.Configuration Reloading 
    Configuration reloading = applying changed configuration without necessarily restarting the Pod.
    Mounted ConfigMap/Secret volume → Kubernetes can update the mounted files.
    Application must reread/watch the file to use the new value.
    Environment variables → do not update in a running container.
    subPath mount → does not receive automatic projected updates.
    If configuration is provided through environment variables, restart/rollout the Pod to get the new value.
    File update by Kubernetes ≠ application automatically reloading it.

    Memory:
    ConfigMap → mounted file → file updates → app reads again → new config

    Short note 📝

        ConfigMap/Secret volume → file can update → application rereads → new config

        Environment variable → no automatic update → restart required

37 Security Context — Short Notes
    Security Context → Controls how a Pod/Container runs and what privileges it has.
    runAsUser: 1000 → Run as Linux user 1000.
    runAsNonRoot: true → Prevent running as root.
    readOnlyRootFilesystem: true → Cannot modify root filesystem.
    allowPrivilegeEscalation: false → Cannot gain higher privileges.
    capabilities → Add/remove specific Linux privileges.
    Can be set at Pod or Container level.
    Main goal → Least privilege: give only the permissions the container needs.

39.Container Lifecycle Hooks — Short Notes
    Lifecycle hooks allow us to perform actions during container startup or shutdown.
    postStart → runs when the container starts.
        Example: print "Container started".
        No guarantee that it runs before the main application.
    preStop → runs before graceful container termination.
        Example: print "Container is going down" or start cleanup.
    preStop time is included in the termination grace period.
    Hooks should be short and safe to repeat.
    If something must happen before the application starts, use an init container.

    Memory:
    postStart → startup action
    preStop → shutdown action
    init container → must finish before app starts

    spec:
        containers:
            - name: app
            image: busybox
            command: ["sh", "-c", "echo 'Application running'; sleep 3600"]

            lifecycle:
                postStart:
                exec:
                    command:
                    - sh
                    - -c
                    - echo "Container has started"

                preStop:
                exec:
                    command:
                    - sh
                    - -c
                    - echo "Container has Dead"

43.Blue-Green vs Canary
                            Blue-Green	            Canary
    Old version	            Running	                Running
    New version	            Running	                Running
    Initial traffic to new	0%	                    Small %
    Traffic switch	        Usually all at once	    Gradually
    Testing with real users	Usually no	            Yes
    Rollback	            Very fast	            Reduce/stop canary traffic
    Main idea	            Switch	                Gradually increase
    Easy way to remember 🧠

    Blue-Green:

    🟦 OLD → 🟩 NEW
    Switch

    Canary:

    🟦 OLD 90% → 🟩 NEW 10%
    Gradually increase

    Kubernetes perspective

    Both strategies can be implemented using Kubernetes Deployments + Services, while more advanced traffic splitting is commonly handled with tools such as Ingress controllers or service meshes.

    Short notes:

    Blue-Green: Run old and new versions → switch all traffic to new version.

    Canary: Run old and new versions → send small percentage of traffic to new version → monitor → gradually increase traffic.

44.ResourceQuota & LimitRange 

    ResourceQuota → Limits total resources of a namespace.
    Example: Namespace can use max 4 CPU + 8Gi memory.
    Can also limit number of Pods, Services, etc.
    LimitRange → Sets resource limits for individual containers/Pods.
    Example: One container can use max 2 CPU + 2Gi memory.
    Can define minimum, maximum, and default CPU/memory.
    🧠 Remember
    Request → Kubernetes reserves this much for the Pod (100m cpu)
    Limit   → Kubernetes won't let it use more than this (500m cpu)

    ResourceQuota = Namespace total limit
    LimitRange = Individual container limit
